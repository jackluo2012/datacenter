## 1. 日常巡检

### 1.1 每日巡检清单

| # | 巡检项 | 方法 | 正常标准 | 异常处置 |
|---|---|---|---|---|
| 1 | 网关存活 | `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8887/datasource/list` | 返回 401（JWT 拦截生效） | 非 401/连接拒绝 → 重启网关并查日志（§1.3） |
| 2 | 管理台登录链路 | `curl -s -XPOST http://127.0.0.1:8887/sys/login -H 'Content-Type: application/json' -d '{"username":"admin","password":"<运维密码>"}'` | code=0 且有 token | 检查 sys.rpc 是否在线（#4） |
| 3 | 全部进程在跑 | 传统：`ps -ef \| grep -E '\-server\|datacenter-server' \| grep -v grep`；compose：`docker compose ps` | 21 个进程（传统）/ 全部 Up（compose） | 对照 01-部署手册 §1.2 端口清单补起缺失进程 |
| 4 | RPC 注册于 etcd | `ETCDCTL_API=3 etcdctl --endpoints=http://127.0.0.1:2379 get --prefix --keys-only "" \| grep rpc`（或逐个 `get datasource.rpc`） | datasource/metadata/datasvc/catalog/quality/metric/tag/job/ide/ai/standard/mdm/ops/theme/security/sys 等 Key 存在 | 缺失项对应服务掉线，重启该服务 |
| 5 | etcd 健康 | `etcdctl --endpoints=http://127.0.0.1:2379 endpoint health` | `is healthy` | `docker compose restart etcd`；数据目录 `./etcd`（传统）损坏时用快照恢复（§2.4） |
| 6 | MySQL 健康 | `mysqladmin -uroot -padmin ping`；`mysql -uroot -padmin -e 'SHOW REPLICA STATUS\G'` | `mysqld is alive`；主从按 §1.2 预留 | 慢/锁等待看 `SHOW PROCESSLIST`；连接数 `SHOW STATUS LIKE 'Threads_connected'` |
| 7 | Redis 健康 | `redis-cli -a admin ping`（compose 容器名 redis；传统注意端口映射） | PONG | Redis 仅缓存，重启无数据损失 |
| 8 | ES 健康 | `curl -s -u elastic:admin http://127.0.0.1:9200/_cluster/health` | status=green/yellow | 磁盘水位 >90% 会只读：清理磁盘后 `curl -XPUT -u elastic:admin http://127.0.0.1:9200/_settings -H 'Content-Type: application/json' -d '{"index.blocks.read_only_allow_delete":null}'` |
| 9 | 日志巡检 | 网关 `nohup.out` / `docker compose logs --since 24h datacenter-api`，grep -E 'ERR\|error\|panic' | 无持续 ERROR 刷屏 | 见 §1.3 定位 |
| 10 | 磁盘水位 | `df -h`（重点 `./data/mysql`、`./etcd`、`./elasticsearch`、Docker 根目录） | < 80% | 超限先清 `dc_*` 日志表（§4）与 Docker 日志（`docker system prune -f`） |
| 11 | 质量任务与调度 | 「数据质量→质量任务」最近状态；DolphinScheduler 控制台实例状态（DS_BASE_URL/ui） | 昨日计划任务全部 passed | failed 任务按 02 手册 §3.5 下钻错误数据；同步告警看 §3 |
| 12 | 审计/登录日志异常 | 「数据运维→登录日志」过滤失败记录 | 无连续失败爆破迹象 | 多次失败锁定来源 IP（防火墙封禁），必要时重置相关账号密码 |

### 1.2 MySQL 主从（预留说明）

当前交付默认**单实例 MySQL**（docker 镜像 mysql:8.4，数据目录 `./data/mysql`）。生产如需主从：

1. 预留架构：应用侧（各服务 `Mysql.DataSource`）只写主库 3306；从库以异步复制挂接，供备份/报表查询；
2. 开启复制：主库 my.cnf 配 `server-id` + `log_bin`（MySQL 8.4 默认已启用 binlog）→ `CREATE USER 'repl'@'%' IDENTIFIED BY ...; GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';` → 从库 `CHANGE REPLICATION SOURCE TO ...`；
3. 本平台服务 DSN 为单点写，**切主时需统一修改各服务 yaml 的 Mysql.DataSource 并滚动重启**（restart.sh 一键拉起）；
4. 交付边界说明：主从搭建与切换属客户侧 DBA 职责，本手册提供备份恢复（§2）兜底。

### 1.3 服务日志路径与常用排查

| 部署 | 日志 |
|---|---|
| 传统（restart.sh） | 网关 `<仓库>/nohup.out`；各 RPC `<仓库>/<服务>/rpc/nohup.out`（如 quality/rpc/nohup.out） |
| compose | `docker compose logs -f --tail=200 <服务名>`；依赖容器同理（mysql/redis/etcd/elasticsearch） |
| DataEase | `./data/dataease/logs/` |
| DolphinScheduler | `./data/dolphinscheduler/` |

排查三板斧：
```bash
grep -c 'level=error' nohup.out                       # 错误量
tail -n 200 nohup.out                                # 网关最近日志
tail -n 200 quality/rpc/nohup.out                    # 具体服务日志
```

### 1.4 调度进程监控

- **平台侧进程**（restart.sh 拉起的 21 个）无 systemd 单元时，建议补一个 crontab 看门狗：

```bash
# 每 5 分钟检查网关与关键 RPC，掉线自动重启（示例）
*/5 * * * * cd /opt/datacenter && (curl -s -o /dev/null http://127.0.0.1:8887/sys/login || (sh restart.sh >> /var/log/dc-watchdog.log 2>&1))
```

- **DolphinScheduler 侧**：standalone 联调镜像 H2 内存库，**容器重启丢项目/工作流/令牌**，生产必须改用 DB 持久化部署（非本交付范围）；监控其 12345 端口与 master/worker 日志；
- **平台调度任务兜底**：质量任务/归档任务的 cron 存于 `dc_quality_job.cron`、`dc_ops_archive_task.cron`，执行历史分别看 `dc_quality_result.run_at`、`dc_ops_archive_log.run_at`——长时间无新记录即调度中断。

## 2. 备份与恢复

### 2.1 备份对象与策略

| 对象 | 位置 | 策略 | 保留 |
|---|---|---|---|
| 业务库 datacenter | MySQL | **每日 mysqldump 全量**（凌晨 2:00）+ binlog 增量 | 全量 30 天，binlog 14 天 |
| MySQL 数据目录 | `./data/mysql`（compose） | 每周停机冷备一次（可选，大库用 xtrabackup） | 2 份 |
| etcd | `./etcd` | 每日快照（注册信息临时态，低风险） | 7 天 |
| ES 索引 | 容器卷 | search 为遗留功能，可重建，不强制备份 | — |
| 代码与配置 | 仓库 + `*/etc/*.yaml` | git 管理；yaml 含密钥，**不得入库**，另行加密备份 | 永久 |

### 2.2 每日全量备份（mysqldump）

```bash
# 1) 写备份脚本 /opt/scripts/dc-backup.sh
cat > /opt/scripts/dc-backup.sh <<'EOF'
#!/bin/bash
set -e
BK=/data/backup/mysql/$(date +%F)
mkdir -p "$BK"
mysqldump -uroot -padmin --single-transaction --routines --triggers \
  --master-data=2 --flush-logs datacenter > "$BK/datacenter_full.sql.gz.tmp"
gzip "$BK/datacenter_full.sql.gz.tmp"
mv "$BK/datacenter_full.sql.gz.tmp.gz" "$BK/datacenter_full.sql.gz"
# 保留 30 天
find /data/backup/mysql -maxdepth 1 -type d -mtime +30 -exec rm -rf {} \;
EOF
chmod +x /opt/scripts/dc-backup.sh

# 2) 定时任务（凌晨 2:00）
crontab -e
0 2 * * * /opt/scripts/dc-backup.sh >> /var/log/dc-backup.log 2>&1
```

要点：
- `--single-transaction`：InnoDB 一致性快照，不锁表；
- `--master-data=2`：记录备份时 binlog 位点，供增量重放；
- 备份校验：`gzip -t` + 每周随机抽一个备份在影子库恢复（§2.4）。

### 2.3 binlog 增量策略

MySQL 8.4 默认启用 binlog。按天增量归档：

```bash
# 备份脚本已 --flush-logs，每日产生新 binlog；归档前一天的 binlog
BINLOG_DIR=/data/mysql   # 容器部署在宿主机 ./data/mysql（含 #innodb_redo 等目录，binlog 形如 binlog.0000XX）
cp -a "$BINLOG_DIR"/binlog.[0-9]* /data/backup/binlog/$(date -d yesterday +%F)/ 2>/dev/null
find /data/backup/binlog -type f -mtime +14 -delete
```

按时间点恢复（PITR）：先恢复全量，再重放 binlog 到目标时刻：

```bash
mysqlbinlog --start-datetime="2026-10-11 02:00:00" --stop-datetime="2026-10-11 15:30:00" \
  /data/backup/binlog/2026-10-11/binlog.0000XX | mysql -uroot -padmin datacenter
```

### 2.4 恢复演练（每季度一次，留档）

```bash
# 1) 影子库恢复
mysql -uroot -padmin -e "CREATE DATABASE IF NOT EXISTS dc_drill DEFAULT CHARSET utf8mb4"
gzip -dc /data/backup/mysql/<日期>/datacenter_full.sql.gz | mysql -uroot -padmin dc_drill

# 2) 核对行数与关键表
mysql -uroot -padmin dc_drill -e "
SELECT COUNT(*) AS ds FROM dc_datasource;
SELECT COUNT(*) AS api FROM dc_api;
SELECT COUNT(*) AS users FROM sys_user;
SELECT COUNT(*) AS audit FROM dc_ops_audit_log;"

# 3) 模拟切回：停写 → 改名切换（演练环境直接切换）
# 4) 记录 RTO（恢复耗时）与 RPO（binlog 缺口），与 04-SLA与培训.md §1 的承诺对标
# 5) 演练后清理
mysql -uroot -padmin -e "DROP DATABASE dc_drill"
```

etcd 快照（辅助）：

```bash
ETCDCTL_API=3 etcdctl --endpoints=http://127.0.0.1:2379 snapshot save /data/backup/etcd/snap-$(date +%F).db
# 恢复（单节点）：etcdctl snapshot restore snap.db --data-dir /etcd-data-new 后重建容器
```

## 3. 告警响应

### 3.1 质量告警 webhook 配置（页面操作）

1. 管理台 →「数据质量」→「告警配置」页签 →「新建通道」；
2. 字段：
   - 通道名称：如「数据质量告警群」；
   - 通道类型：`dingtalk`（钉钉机器人）/ `feishu`（飞书机器人）（email 为表结构预留，当前未实现）；
   - Webhook：机器人地址，需以 `http(s)://` 开头（如 `https://oapi.dingtalk.com/robot/send?access_token=...`）；
   - 加签密钥：钉钉「加签」安全设置的 `SEC` 开头密钥（可选；配置后平台自动拼接 timestamp+sign，算法 `base64(hmac-sha256(key=secret, msg="{ts}\n{secret}"))`）；飞书同理填加签 secret；
   - 最低告警级别：`failed`（任务最终失败才告警）/ `partial`（存在部分通过的规则即告警，含 failed）；
3. 保存后打开「启用状态」开关，点「发送测试」验证连通（弹窗回显机器人返回信息）；
4. 触发链路：质量任务执行完成 → 逐通道按 min_level 判定 → 推送文本（任务名/状态/通过率/失败规则明细）→ 落 `dc_quality_alert_log`（status=success/failed，msg）。

### 3.2 告警响应分级与处置

| 级别 | 场景 | 响应 | 处置动作 |
|---|---|---|---|
| P0 | 网关不可用/MySQL 宕机，平台整体不可访问 | 15 分钟内响应 | 01-部署手册 §2.5 排查表；恢复失败走 §2 数据恢复；同步客户干系人 |
| P1 | 调度/质量任务连续 failed、数据服务大面积 error | 30 分钟内响应 | 看错误数据样本定位脏数据；检查源库可用性；必要时下线相关 API |
| P2 | 单条质量规则不通过、告警发送失败（dc_quality_alert_log.status=failed） | 4 小时内响应 | 核对 webhook/加签；规则阈值不合理则调整规则参数 |
| P3 | 日志表增长过快、磁盘水位预警 | 下一工作日 | 执行 §4 容量管理 |

### 3.3 告警通道自身监控

```sql
-- 最近 24h 告警发送情况
SELECT status, COUNT(*) FROM dc_quality_alert_log
WHERE sent_at > NOW() - INTERVAL 24 HOUR GROUP BY status;
-- 查看失败原因
SELECT channel_id, job_id, msg, sent_at FROM dc_quality_alert_log
WHERE status='failed' ORDER BY sent_at DESC LIMIT 20;
```

发送持续 failed 时：检查网络出站（机器人域名可达）、secret 是否更换过、webhook 是否被封禁。

## 4. 容量管理（dc_* 日志表清理）

### 4.1 日志类表与增长来源

| 表 | 内容 | 写入来源 | 增长速度参考 |
|---|---|---|---|
| dc_api_call_log | 数据服务每次调用 | /datasvc/execute 链路 | 与调用量线性相关（高频 API 日万行级） |
| dc_ops_audit_log | 管理面写操作审计 | 网关审计切面（POST/PUT/DELETE） | 低-中 |
| dc_ops_login_log | 登录日志 | 登录成功/失败 | 低 |
| dc_quality_result | 质量任务逐规则结果 | 任务执行 | 规则数 × 执行频次 |
| dc_quality_alert_log | 告警发送记录 | 告警推送 | 低 |
| dc_quality_error_data | 错误样本（rows_json，≤100 行/条） | 失败规则采样 | 中（JSON 较大） |
| dc_quality_profile | 表剖析与健康分 | 健康分分析 | 低-中 |
| dc_ask_log | AI 问数审计 | /ai/ask、/ai/ask_and_run | 与问数频次相关 |

### 4.2 清理 SQL（保留 90 天为例，分批删除防大事务）

> 全部为幂等脚本，建议放入每周维护 cron（业务低峰执行）。执行前确认已过审计保留期要求（等保日志留存按客户合规要求，通常 ≥ 6 个月——如需 6 个月请把 INTERVAL 90 DAY 调整为 180 DAY）。

```sql
-- 通用分批删除模板（每批 5000 行，循环直至无行）
-- 1) 数据服务调用日志（索引 idx_api_time 含 created_at，可高效过滤）
DELIMITER $$
CREATE PROCEDURE dc_purge_api_call_log(IN keep_days INT)
BEGIN
  REPEAT
    DELETE FROM dc_api_call_log
    WHERE created_at < NOW() - INTERVAL keep_days DAY
    LIMIT 5000;
  UNTIL ROW_COUNT() = 0 END REPEAT;
END$$
DELIMITER ;

-- 2) 其余日志表逐一执行（先执行一次建过程，或直接用多语句）
CALL dc_purge_api_call_log(90);

-- 审计与登录日志（等保一般要求留存 ≥ 6 个月，此处示例 180 天）
DELETE FROM dc_ops_audit_log  WHERE created_at < NOW() - INTERVAL 180 DAY LIMIT 5000;  -- 多次执行直至 0 行
DELETE FROM dc_ops_login_log  WHERE created_at < NOW() - INTERVAL 180 DAY LIMIT 5000;

-- 质量执行类（保留 90 天）
DELETE FROM dc_quality_result      WHERE run_at     < NOW() - INTERVAL 90 DAY LIMIT 5000;
DELETE FROM dc_quality_alert_log   WHERE sent_at    < NOW() - INTERVAL 90 DAY LIMIT 5000;
DELETE FROM dc_quality_error_data  WHERE run_at     < NOW() - INTERVAL 90 DAY LIMIT 5000;
DELETE FROM dc_quality_profile     WHERE ran_at     < NOW() - INTERVAL 90 DAY LIMIT 5000;
DELETE FROM dc_ask_log             WHERE created_at < NOW() - INTERVAL 90 DAY LIMIT 5000;

-- 3) 清理后回收表空间（可选，锁表谨慎，低峰执行）
OPTIMIZE TABLE dc_api_call_log, dc_ops_audit_log, dc_quality_result;

-- 4) 删除临时过程
DROP PROCEDURE IF EXISTS dc_purge_api_call_log;
```

维护 cron 示例（每周日 3:00）：

```bash
0 3 * * 0 mysql -uroot -padmin datacenter < /opt/scripts/dc-purge.sql >> /var/log/dc-purge.log 2>&1
```

### 4.3 业务数据归档（页面化能力）

平台内已内置归档任务能力（「数据运维 → 归档任务」）：把源表历史数据按条件搬到归档表并可选删源，分批执行。业务大表（如订单类 `dm_orders`/自建业务表）的长期容量治理优先用该能力，日志表用 §4.2 SQL。

### 4.4 磁盘与容器层清理

```bash

# 长效：daemon.json 配置 {"log-opts":{"max-size":"50m","max-file":"3"}} 后重启 docker
```

## 5. 应急预案速查

| 故障 | 立即动作 | 恢复后 |
|---|---|---|
| 网关进程崩溃 | `sh restart.sh`（传统）/ `docker compose up -d datacenter-api` | 查 nohup.out 定位根因，按 01 手册 §6 决定是否回滚 |
| MySQL 数据损坏 | 停全部服务 → 最近全量 + binlog 恢复（§2.3/§2.4） | 演练记录补档；排查磁盘/内存故障源 |
| etcd 数据丢失 | 重建 etcd 容器（服务自动重注册） | 无需人工补数据（注册为临时态） |
| Redis 缓存污染 | `redis-cli -a admin FLUSHALL` | 观察缓存命中率回升 |
| 质量告警风暴（误报） | 停用告警通道开关 | 修规则阈值/告警级别后再启用 |
| 误删数据源/规则 | 平台无回收站：从 `dc_ops_audit_log`（detail_json 含 body 摘要）找回参数重新录入 | 建议关键操作前备份库 |
